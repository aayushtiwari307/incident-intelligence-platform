### Why multer 2.0.0 is not the answer and why an earlier override "did nothing"

The archive's root `package.json` contains no multer override at all (static). The only way a root override fixes this is with an exact entry for `multer` and a regenerated lockfile. Whatever earlier attempts did is not visible in the archive. Typical causes if you retry: the override sat in a workspace `package.json` (npm only honours the **root** one), or `npm ci` was run against an old lockfile, or the override range did not cover the exact pin.

### Zod reachability (static, from reading the code)

| Entry point | Bound before zod sees the data |
|---|---|
| Alertmanager webhook | Authenticated **before** the body is read; body capped at the webhook limit (1 MiB default); the alert count is checked against `ALERTMANAGER_MAX_ALERTS_PER_REQUEST` **before** zod validates elements. |
| Ordinary JSON API | Global body limit 64 KiB (`config.http.bodyLimitBytes`). |
| AI output validation | Output size is checked against `AI_LIMITS.maxOutputChars` before zod parses it; provider token caps apply on top. |
| Web | `apps/web` does not import zod directly or declare it (static); it can only reach it through `packages/shared`, in the browser, so it is not a server memory risk. |

Whether zod 3.x code is genuinely exposed is itself disputed in the advisory discussions found: one source says the vulnerable `$ZodArray` code exists only in zod 4's core, others report that 3.x falls inside the advisory range and has no patched 3.x release (3.25.76 is the last 3.x). `npm audit` flags it by range. The primary advisory page could not be read here, so treat 3.x exposure as **unverified** and the practical risk as low and bounded.

### Zod 4 migration plan (when it can be tested)

1. Branch; on a machine with registry access install `zod@4.6.7` (or newer; check `npm view zod dist-tags`) only in `packages/shared` first.
2. Migrate schema by schema. Known zod 3 to 4 differences to check in every consumer: `error.errors` is `error.issues`; `.flatten()`/`.format()` and `message:` options are deprecated in favour of `z.treeifyError` and the `error` option; `z.record` needs two arguments; `.strict()`/`.email()` still work but are deprecated; default and optional semantics changed; `ZodTypeDef` is gone.
3. Before touching code, snapshot the current accept/reject behaviour: write a table-driven test that feeds every request schema and the AI output schema the same accepted and rejected payloads and records issue paths. Re-run it after each schema.
4. `validationFailed(...)` in `apps/api/src/common/errors.ts` turns zod issues into field errors; keep its output identical (the web forms depend on it).
5. Done when typecheck, lint, all unit tests and all integration tests pass and the behavior table is unchanged. Then remove the root `"zod": "3.25.76"` override.

## Commands to apply the multer override (Windows cmd.exe, repository root, registry access needed)

```bat
copy package.json package.json.bak
copy package-lock.json package-lock.json.bak
npm view multer version dist-tags
npm view @nestjs/platform-express dist-tags
npm view @nestjs/platform-express@latest dependencies.multer
```

Only if `npm view multer versions` lists `2.5.0` and no newer platform-express already depends on it: edit the root `package.json`, add `"multer": "2.5.0"` inside the existing `"overrides"` object, then:

```bat
npm install --package-lock-only
npm ls multer
npm ci
npm run typecheck
npm run lint
npm test
npm audit --json > %TEMP%\audit-after.json
```

`npm ls multer` must show `2.5.0` for the `@nestjs/platform-express` dependency (marked `overridden`). Never run `npm audit fix --force`. If anything fails, restore the two `.bak` files.
