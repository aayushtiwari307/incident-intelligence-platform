# 0010 Authentication, sessions, roles and the incident workflow (Milestone 1)

**Status.** Product implementation delivered; execution of the real NestJS wiring, `pg` pool, and Next.js production build remains unverified for the Milestone 1 ZIP. The original authoring sandbox used a PostgreSQL 16 instance through a `psql`-backed adapter for service/handler tests; see the explicit verification boundary below. The Redis-backed rate limiter described below has since been implemented with a dedicated real-Redis test suite separate from ordinary API unit tests. The suite requires a loopback PostgreSQL test URL for its authentication cases; its execution result must be taken from the relevant local or CI run, not inferred from this decision record.

## Decisions

| Area | Decision | Why / rejected alternative |
|------|----------|----------------------------|
| Session | Opaque 256-bit random token in an `HttpOnly; SameSite=Lax` cookie (`sid`, `__Host-sid` + `Secure` in production). Only `SHA-256(token)` is stored in `auth_sessions.token_hash`. | A DB leak or a log line cannot be replayed as a session. Rejected: JWT in `localStorage` (readable by any XSS, not revocable). Rejected: JWT cookie (revocation needs a server table anyway). **Interview concept: server-side session vs stateless JWT.** |
| Revocation | Logout sets `revoked_at`; the role is read **live** from `memberships` on every request. | A demotion or removal applies on the next request, not at token expiry. |
| Passwords | `scrypt` from Node's `crypto` (N=2^15, r=8, p=3, per-hash salt, NFKC-normalised), constant-time compare, a dummy verify for unknown emails, rehash-on-login when parameters change. | No new native dependency (bcrypt/argon2 would need a lockfile change that could not be generated here). Unknown-email and wrong-password responses are identical. |
| CSRF | `SameSite=Lax` **plus** an `Origin` allow-list check on every unsafe method (allow-list = `CORS_ORIGINS`). A missing `Origin` is allowed (non-browser client, cannot be CSRF). | Defence in depth without a token round-trip. |
| Rate limiting | Async `RateLimiter` interface with an in-memory sliding-window implementation and a Redis Sorted Set implementation. Redis identities are SHA-256 hashed; atomic Lua scripts remove expired entries, enforce the window, execute `consume()`, `peek()` and `reset()`, and set key TTLs. `REDIS_URL` unset keeps in-memory limiting. If Redis is configured but unavailable, login IP, login account+IP, registration IP, failed webhook authentication and AI use fail-closed responses; the two Alertmanager limiters fall back to in-memory limiting. | Redis-backed distributed limiting is implemented, but Render currently runs one API instance and no production Redis/Valkey deployment has been configured or verified. |
| Tenancy | The organization is taken from the session's active organization only; no handler or service reads an organization id from body, query or path. Foreign ids are 404 (indistinguishable from missing). Assignee must be a member of the same organization (composite FK `incidents_assignee_membership_fkey`). | See 0004. Integration tests cover cross-tenant get/update/transition/comment/timeline/list/assign. |
| Roles | `viewer < responder < admin < owner`. The permission table lives in `@platform/shared` and is used by the API (enforcement) and the UI (hiding controls only). Admins cannot touch owners or change their own role. The "organization keeps an owner" invariant is a deferred trigger + advisory lock (0009). | The UI copy of the rules exists only to avoid showing buttons that would fail. |
| Invitations | Single use, bound to the invited email, hashed token, 7 days default, owners are not invitable; redemption failures look like the same 404. First-time invitees can register directly into the invited organization; existing users can follow the same invitation link, sign in, and accept it, or accept manually from Team. The token is shown once to the inviting admin; **no email is sent** (no mail provider yet). | Redemption is serialized with `FOR UPDATE`. |
| Incidents | Per-organization numbers from a counter row (20 parallel creates → 20 gap-free numbers). Optimistic concurrency via `version` (`expectedVersion` → 409 `VERSION_CONFLICT`). Status graph enforced in the service **and** a DB trigger; a test compares both across all 25 pairs. Timeline is append-only (DB triggers). | **Interview concepts: optimistic concurrency control, state machine enforced at two layers, append-only audit log, per-tenant sequence without gaps/duplicates.** |
| HTTP layer | All rules live in framework-free `ApiHandlers`; Nest controllers only translate Express objects. One exception filter maps `AppError` to `{error:{code,message,details}}`; anything else is a generic 500 and is logged with secrets redacted. | Makes the behaviour testable against a real database without booting Nest. |
| Frontend | Next.js client components, plain CSS (light/dark, visible focus, skip link, landmarks, labelled forms, `role=alert` errors). No new dependency. | Tailwind / component libraries were deferred: each would change the lockfile. |
| Dependencies | The initial Milestone 1 / 1.1 code changes added no dependencies. The implementation retains a root lockfile and later added the official Redis client package and Redis-specific tooling for the distributed limiter. | Dependency additions must be reflected in the lockfile and verified by the existing dependency checks. |

## Milestone 1.1 correctness corrections

- **Member removal and incident audit trail:** removing a member now locks their membership, locks any incidents assigned to them, clears those assignments and appends an `assigned` timeline event for each change in the same PostgreSQL transaction. Events record the removed member snapshot, a null destination, and `reason: "member_removed"`. Incident versions are incremented by the database update trigger. If removing the member violates the last-owner invariant at commit, unassignments and events roll back with the membership deletion.
- **Concurrent assignment/removal:** an incident update that sets a non-null assignee takes a `FOR KEY SHARE` lock on that membership before locking the incident. Member removal takes `FOR UPDATE` on the same membership before locking affected incidents, so a concurrent assignment either commits first and is then audited as unassigned, or fails after removal. The database composite foreign key remains the final integrity check.
- **First-time invitee registration:** `POST /api/auth/register-with-invite` validates and locks the one-time invitation, then creates the user, membership, accepted-invite marker, and session atomically. It does not create a separate organization. The UI exposes a registration link containing the token in the URL fragment (not sent in HTTP requests); the fragment is removed from the address bar after the client captures it. New invitees register directly into the invited organization. Existing accounts can follow the same link, sign in, and have the invite accepted after successful authentication.
- **Atomicity:** real PostgreSQL integration tests cover both successful member removal with timeline events and rollback when a last-owner removal is rejected; invite-registration tests cover direct membership creation and wrong-email rejection without consuming the invitation.

## Redis rate-limit implementation status

The deferred Redis implementation is now implemented as the separate Redis Sorted Set implementation of the existing async rate-limiter interface. Random request IDs are unique Sorted Set members and Redis server time is used for scores and sliding-window boundaries. Lua scripts perform atomic removal, counting and TTL updates. Redis keys include a fixed application prefix, version, distinct policy namespace and SHA-256 identity hash. Rejected requests are not added, `peek()` does not increment, and `reset()` removes only that policy's key.

The production limits are login IP 100/15 minutes, login account+IP 5/15 minutes, registration IP 10/hour, Alertmanager IP 600/minute, failed webhook authentication 20/5 minutes, Alertmanager integration 300/minute, and AI user 5/10 minutes. The test environment has a registration IP override of 10,000/hour only; it does not replace production limits.

Outage policy is explicit. With `REDIS_URL` unset, the application uses the existing in-memory limiter. If `REDIS_URL` is configured but Redis is unavailable, login, registration, failed webhook authentication and AI fail closed without exposing Redis errors. Alertmanager IP and integration use in-memory fallbacks. A valid Alertmanager credential is not rejected only because the failed-authentication Redis preflight is unavailable; an invalid credential still fails closed when its failure cannot be counted. TCP connection establishment is capped at 1 second; the full Redis handshake and each dispatched command have separate 5-second absolute deadlines. Commands waiting to be written have a 1-second queue timeout. Timed-out operations destroy their client, offline queuing is disabled, and a subsequent request reconnects after a short cooldown. Redis server time is authoritative for the windows. The AI burst limit is global per user across organizations.

Local development Redis is provided by the existing `docker-compose.yml` service on loopback port 6380 (`docker compose up -d redis`). Configure the API with `REDIS_URL=redis://127.0.0.1:6380`. GitHub Actions starts Redis 7-alpine on port 6379 and runs the dedicated real-Redis Jest suite with `npm run test:redis -w @platform/api`. Redis is not mandatory for ordinary unit tests or application startup. Render currently runs one API instance; production multi-instance deployment and Render Valkey 8 configuration remain unverified and have not been configured.

## Known limitations (deliberate, documented)

- Registration reveals whether an email is already registered (409). Acceptable for now; mitigated only by the IP rate limit. Fixing it needs email verification.
- No password reset, no email verification, no MFA, no session list / "sign out everywhere" UI.
- With `REDIS_URL` unset, rate limiting is in-memory (above). Behind a proxy, `TRUST_PROXY_HOPS` must be correct or all clients share one IP. Redis outage behavior is documented in the implementation-status section.
- For local development open the web app and API on the **same host name** (`http://127.0.0.1:3000` with the API on `127.0.0.1:3001`). `localhost` and `127.0.0.1` are different *sites*, and a `SameSite=Lax` cookie is not sent on cross-site `fetch`, so sign-in would appear to succeed and the next request would be 401.
- RLS is still deferred (0004). Socket.IO real-time updates are implemented using PostgreSQL `LISTEN/NOTIFY`. The AI suggestion integration is implemented, but is not implied to be enabled on the public demo. The job queue remains PostgreSQL-backed and is independent of Redis rate limiting; BullMQ is not used.
